# 공고모아 — 정부지원사업 통합 조회

기존 v1/v2를 고치는 방식이 아니라, 처음부터 다시 만든 로컬 웹앱입니다.
Windows PowerShell에서 바로 실행되도록 설계했습니다.

## 핵심 구조

- `server.py` : 로컬 웹서버 + API 서버
- `collector.py` : 기업마당/나라장터 전용 수집기, 게시판 수집기, 전체 수집 오케스트레이션(`collect_all()`)
- `recipe_engine.py` : LLM이 사이트 구조를 한 번 분석해 만든 "레시피"(선택자/필드 매핑)로 매 수집을 결정적으로 실행. 새 사이트 등록과 "사이트 구조 변경으로 수집이 깨짐" 복구가 둘 다 이 엔진을 씀
- `funding_classifier.py` : K-Startup 공고가 실제 스타트업 대상 자금·펀딩인지 LLM으로 판정(keep/exclude), elig(연차/지역/분야) 계산도 겸함
- `llm.py` : litellm 기반 모델-불특정 LLM 호출 계층 — Anthropic/OpenAI 등 공급자를 하나의 인터페이스로 통일
- `scheduler.py` : 관리자가 설정한 시간/주기에 맞춘 자동 재수집
- `database.py` : SQLite 저장소
- `auth.py` : 비밀번호 해시, 사용자 API 키 암호화, 세션 토큰
- `ai_match.py` : 등록된 LLM 모델/키로 회사 맞춤 공고 적합도 판정 (`llm.py`를 통해 모델-불특정으로 호출, 사용자 본인 키 사용)
- `uploads.py` : 회사 문서(PDF/DOCX/TXT/MD) 업로드 파싱, 텍스트 추출
- `static/` : 화면 UI
- `data/gongo.sqlite` : 실행 후 자동 생성되는 DB
- `config.json` : 수집 설정/API 키 (git에는 올라가지 않음, `.gitignore` 참고)

계정 가입 후 로그인하면 회사 정보/즐겨찾기/AI 분석 결과가 계정별로 분리되어 저장됩니다.
AI 맞춤 분석은 각자 자신의 LLM API 키를 "회사 정보" 화면에 등록해서 사용합니다 (관리자 키를 공유하지 않음). 여러 모델/키를 등록해두고 그중 하나를 활성으로 골라 쓸 수 있습니다.
기업마당(bizinfo) 공고는 등록된 사용자의 키로만 수집되고, 조회하는 사용자 본인도 키를 등록해야 볼 수 있습니다.

## 화면 구성

왼쪽 사이드바에 5개 탭이 있습니다.

- **공고 목록** : 전체 공고를 검색/필터링해서 봅니다. 소스, 접수 상태, AI 적합도로 필터링할 수 있습니다. K-Startup 공고 중 자금성 판정에서 exclude된 것과, 관리자가 꺼둔 소스의 공고는 기본적으로 안 보입니다(뒤에 자세히 설명).
- **관심 공고** : 별표를 누른 공고만 모아봅니다.
- **캘린더** : 마감일 기준으로 이번 달 공고를 달력으로 봅니다. 날짜를 클릭하면 그 날 마감인 공고만 필터링되고, 같은 날짜를 다시 클릭하거나 다른 날짜를 클릭하면 필터가 바뀝니다.
- **회사 정보** : 회사 프로필(업력/지역/분야/키워드 등), AI 모델/API 키(여러 개 등록 후 활성 선택 가능), 기업마당 API 키, 회사 문서(PDF/DOCX/TXT/MD)를 등록합니다. 여기서 "AI로 맞춤 공고 분석 실행"을 누르면 화면에 실제로 보이는 공고 전체에 대해 적합/확인/부적합 판정이 붙습니다.
- **관리자** : `ADMIN_EMAILS`에 등록된 계정에서만 보입니다. 수동 재수집, 소스별 수집 상태(수집 건수/표시 건수 구분), 소스 활성화·비활성화, 소스 URL 재정의, URL만으로 새 소스 등록(AI가 자동으로 수집 방법을 찾아냄), 자동 수집 일정을 다룹니다.

## 바로 실행

저장소를 클론한 폴더에서:

```powershell
powershell -ExecutionPolicy Bypass -File .\start-server-v7.ps1
```

브라우저:

```text
http://127.0.0.1:8080
```

서버를 끄려면 실행 중인 PowerShell에서 `Ctrl + C`.

## 수집 설정

`config.json`에서 필요한 소스만 `enabled: true`로 둡니다.

K-Startup, 한국연구재단(NRF), 국가신약개발사업단(KDDF), 서울바이오허브(biohub_direct)는 API 키를 쓰지 않고 저장된 "레시피"(`recipe_engine.py`)로 웹페이지를 직접 읽습니다. 레시피는 LLM이 사이트 구조를 한 번 분석해서 만든 선택자/필드 매핑이고, 그 이후 매 수집은 레시피만으로 결정적으로(추가 LLM 호출 없이) 실행됩니다. 사이트 구조가 바뀌어 수집이 갑자기 0건이 되면 관리자 화면에 "⚠ 이상감지"가 뜨고, 저장된 레시피 재시도 → 실패 시 LLM 재발견 순서로 자동 복구를 시도합니다.

```json
"kstartup": {
  "enabled": true,
  "method": "html",
  "list_url": "https://www.k-startup.go.kr/web/contents/bizpbanc-ongoing.do",
  "max_pages": 5,
  "max_items": 80
}
```

K-Startup은 수집 직후 `funding_classifier.py`가 각 공고의 상세 페이지(지원분야/창업업력/신청대상/지원내용)를 가져와 "스타트업이 신청할 수 있는 실제 현금성 자금·펀딩"인지 LLM으로 판정합니다. 컨설팅·멘토링·사무공간 입주·투자자 매칭처럼 자금이 아닌 지원만 있는 공고는 exclude로 분류되어 화면에서 숨겨지고, 지원금·바우처·융자·확정 상금·확정 투자 같은 실제 현금성 지원이 있고 창업 연차 자격도 맞는 공고만 노출됩니다. 판정 전 공고(새로 수집됐지만 아직 분류되지 않음)는 숨겨지지 않고 그대로 보입니다.

기업마당은 `enabled: true`로만 켜면 됩니다. API 키는 더 이상 여기에 두지 않습니다 —
등록된 사용자 중 "회사 정보" 화면에서 본인의 기업마당 API 키를 저장한 사람이 있어야
수집기가 그 키로 데이터를 가져옵니다 (관리자가 등록해두는 것을 권장). 등록된 키가
하나도 없으면 이 소스는 건너뜁니다.

```json
"bizinfo": {
  "enabled": true,
  "page_unit": 200
}
```

나라장터(조달청 입찰공고)도 [공공데이터포털](https://www.data.go.kr/data/15129394/openapi.do)에서 발급받은 서비스키가 있을 때만 켭니다. 전국 물품/용역 입찰공고 전체를 가져오면 수천 건씩 쏟아지므로, `keywords`에 매칭되는 공고만 걸러서 가져옵니다.

```json
"g2b": {
  "enabled": true,
  "serviceKey": "발급받은_나라장터_서비스키",
  "days": 3,
  "keywords": ["바이오", "헬스", "의료", "신약", "R&D"]
}
```

키가 없는 소스나 URL이 맞지 않는 소스는 실패로 앱 전체를 죽이지 않습니다. 수집 결과가 하나도 없으면 샘플 공고가 표시됩니다.

## 관리자 기능

`ADMIN_EMAILS` 환경변수(쉼표로 구분한 이메일 목록)에 등록된 이메일로 가입/로그인하면 그 즉시 자동으로 관리자 권한이 부여됩니다. 별도의 승인·초대 절차나 화면 안에서 다른 사용자를 관리자로 지정하는 기능은 없습니다 — 관리자가 되려면 배포 환경변수에 이메일이 미리 등록되어 있어야 합니다.

- **소스 상태 — 수집 건수 vs 표시 건수**: 관리자 화면 소스 상태 표는 "수집 건수"(이번 실행에서 원본 사이트로부터 병합·제외 반영 전 몇 건을 긁어왔는지)와 "표시 건수"(중복 병합, K-Startup 자금성 판정 제외, 소스 비활성화까지 전부 반영한 뒤 실제로 화면에 뜨는 건수)를 구분해서 보여줍니다. 두 값이 다른 게 정상입니다.
- **소스 활성화/비활성화**: K-Startup/기업마당/나라장터/NRF/KDDF/서울바이오허브/KHIDI를 관리자 화면에서 개별적으로 켜고 끌 수 있습니다. 꺼둔 소스의 기존 공고는 DB에서 지워지지 않고 목록에서만 숨겨지므로, 다시 켜면 바로 복원됩니다.
- **소스 URL 재정의**: 관리자 화면 "소스 URL 재정의" 패널에서 위 소스들의 수집 URL을 코드 수정·재배포 없이 교체할 수 있습니다. 사이트 주소가 바뀌었을 때 임시로 대응하는 용도이며, 비워두고 저장하면 `config.json`의 기본값으로 돌아갑니다. 사이트 URL은 그대로인데 내부 HTML 구조만 바뀐 경우는 이 기능으로 해결되지 않고, 저장된 레시피가 자동으로(또는 이상감지 시) 재발견되거나 `collector.py`의 파서 수정이 필요합니다.
- **URL만으로 새 소스 등록**: 이름과 공고 목록 페이지 URL만 입력하면 별도 코드 작성 없이 AI가 자동으로 수집 방법(레시피)을 찾아냅니다. 미리보기를 확인하고 확정해야 실제 수집에 반영되며, 등록 후에는 이름/URL 수정, 활성화/비활성화, 삭제가 가능합니다.
- **자동 수집 일정**: 서버가 계속 실행 중인 동안 매일 지정 시간 또는 일정 주기(시간 단위)로 자동 재수집하도록 설정할 수 있습니다.
- **수집 이상감지**: 매 수집마다 소스별 건수 이력을 남겨서, 최근 평균 대비 이번 건수가 0이거나 크게 급감하면(단, 관리자가 의도적으로 꺼둔 소스는 제외) 관리자 화면 소스 상태 표에 "⚠ 이상감지" 배지가 뜹니다. 진짜 공고가 없는 것인지 스크래핑이 깨진 것인지 구분하는 용도이며, 레시피 기반 소스는 이 배지가 뜨면 자동 복구도 함께 시도됩니다.

**예정된 변경(아직 미구현):** 운영 환경에서는 공고 갱신을 자동 수집 일정에만 맡기고, 수동 재수집은 관리자 계정만 쓸 수 있게 좁힐 예정입니다(지금은 로그인한 사용자 누구나 `업데이트` 버튼으로 재수집을 트리거할 수 있음). 이 변경이 들어가면 수집·레시피 발견에 쓰이는 LLM 키도 함께 정리되어, 지금처럼 트리거한 사용자의 활성 키를 우선 쓰는 대신 로그인 여부와 무관하게 항상 관리자 키를 쓰도록 바뀔 예정입니다(`database.resolve_background_llm_profile()` 참고).

## AI 모델 / API 키

AI 맞춤 분석, 신규 소스 레시피 발견 등 앱 안의 모든 LLM 호출은 `llm.py`가 [litellm](https://github.com/BerriAI/litellm)을 통해 공급자와 무관하게 처리합니다. "회사 정보" 화면에서 Anthropic/OpenAI 등 원하는 모델의 API 키를 등록하면 되고, 여러 개(이름/모델/키) 등록해두고 그중 하나를 "활성"으로 골라 쓸 수 있습니다. 키는 암호화되어 저장되고 화면에 다시 표시되지 않습니다. 로그인한 사용자가 트리거한 수집(수동 재수집 등)은 그 사용자의 활성 키를 쓰고, 사용자 없이 실행되는 백그라운드 자동 수집은 등록된 관리자 중 가장 최근에 승격된 계정의 키로 대체됩니다.

## 회사 문서 기반 AI 매칭

"회사 정보" 화면에서 회사소개서·인증서·실적자료 등을 업로드하면(PDF/DOCX/TXT/MD, 파일당 8MB, 계정당 최대 10개) 텍스트를 추출해 DB에 저장하고, AI 맞춤 분석 시 6개 기본 필드보다 훨씬 풍부한 근거로 판단합니다. 원본 파일은 저장하지 않고 추출된 텍스트만 남습니다. AI 맞춤 분석은 화면에 실제로 보이는 공고(자금성 판정 exclude, 비활성화된 소스는 제외)에 대해서만 실행되어 불필요한 LLM 호출을 하지 않습니다. Anthropic 모델을 쓸 경우 문서가 많아져도 청크마다 반복 과금되지 않도록 프롬프트 캐싱(`cache_control`)이 자동 적용됩니다.

## 상태 확인

서버가 켜져 있을 때 새 PowerShell에서:

```powershell
Invoke-RestMethod http://127.0.0.1:8080/api/health
Invoke-RestMethod -Method Post http://127.0.0.1:8080/api/recollect | ConvertTo-Json -Depth 10
```

## 핵심 설계 결정

1. 파일 기반 캐시(`gongo_feed.json`) 대신 SQLite 하나만 사용합니다.
2. `collect.py`를 subprocess로 띄우지 않고, 서버가 collector를 직접 import해서 실행합니다 (인코딩 문제 회피).
3. 소스 하나가 실패해도 전체 수집이 죽지 않습니다 — 실패한 소스만 건너뜁니다.
4. API 키가 없을 때도 앱은 뜨고, 샘플 데이터로 확인 가능합니다.
5. 관심 공고/AI 판정 결과는 localStorage가 아니라 계정별로 SQLite에 저장됩니다.
6. CSV 내보내기를 기본 제공합니다.

## 주의

- `config.json`은 실제 API 키가 들어갈 수 있으므로 GitHub에 올리지 마세요 (`.gitignore`에 이미 포함).
- K-Startup/NRF/KDDF/서울바이오허브는 레시피 기반 수집(`recipe_engine.py`)이라 robots.txt 또는 사이트 구조 변경에 따라 막힐 수 있으며, 이 경우 이상감지 후 자동 복구를 시도합니다.
- KHIDI(`khidi_direct`)는 레시피가 아니라 전용 파서로 직접 수집합니다 — 공개 openAPI 피드가 본문 텍스트를 주지 않아 제목 문자열에서 신청기간을 정규식으로 해석해야 하기 때문입니다. 기업마당·나라장터도 각자 API 키 기반 전용 수집기(`collect_bizinfo()`/`collect_g2b()`)를 쓰고 아직 레시피로 옮기지 않았습니다. 기업마당 API 결과를 키워드로 라우팅하는 것은 보조 수단으로, KHIDI 전용 파서가 놓친 공고를 보완하는 용도입니다.
- 기업마당은 별도 공용 키를 두지 않습니다 — 등록된 사용자 중 "회사 정보"에서 본인의 기업마당 API 키를 저장한 사람이 있어야 수집됩니다. 화면에서 기업마당 공고를 보려면 조회하는 사용자 본인도 키를 등록해야 합니다.
- 사용자 비밀번호는 해시로만 저장되고, 사용자가 등록한 AI 모델 API 키/기업마당 API 키는 `APP_SECRET_KEY`로 암호화되어 저장됩니다. 화면에 다시 표시되지 않습니다.

## 배포 (Railway / Render 등 관리형 플랫폼)

1. **Git 저장소 준비**
   ```powershell
   git init
   git add .
   git commit -m "Initial commit"
   ```
   `config.json`과 `data/`는 `.gitignore`에 있어서 커밋에 포함되지 않습니다. 커밋 후 `git status`로 실제 API 키나 `data/gongo.sqlite`가 올라가지 않았는지 한 번 확인하세요.
2. GitHub에 새 저장소를 만들고 위 로컬 저장소를 push합니다.
3. Railway/Render에서 "새 프로젝트 → GitHub 저장소 연결"로 이 저장소를 선택합니다.
4. **환경변수** 설정 (플랫폼의 Variables/Environment 설정 화면에서):
   - `APP_SECRET_KEY` — 사용자 API 키 암호화에 쓰는 비밀키. 아래 명령으로 한 번 생성해서 그대로 붙여넣으세요.
     ```powershell
     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
     ```
     이 값을 잃어버리면 이미 저장된 사용자들의 API 키를 복호화할 수 없게 되니, 별도로 안전하게 보관하세요.
   - `G2B_API_KEY` — 나라장터(조달청) 서비스키를 쓰려면 설정 (선택). 기업마당은 환경변수를 쓰지 않고, 배포 후 관리자 계정으로 로그인해 "회사 정보"에서 키를 등록하세요.
   - `ADMIN_EMAILS` — 관리자 권한을 자동으로 부여할 이메일 목록, 쉼표로 구분 (선택). 예: `me@example.com,teammate@example.com`
5. **퍼시스턴트 볼륨**을 `data/` 경로에 연결하세요. SQLite 파일(`data/gongo.sqlite`)이 재배포/재시작 후에도 유지되려면 반드시 필요합니다.
6. 시작 커맨드는 `Procfile`에 정의되어 있습니다: `python server.py --host 0.0.0.0 --port $PORT` — 대부분의 플랫폼이 `Procfile`을 자동 인식합니다.
7. 배포 후 도메인으로 접속해서 회원가입 → 로그인 → AI 모델 API 키 등록까지 되는지 확인하세요.


## 레시피 기반 수집 (K-Startup / NRF / KDDF / 서울바이오허브)

이 네 소스는 사이트 전용 파서를 손으로 짜는 대신, LLM이 사이트 구조를 **한 번** 분석해서 만든
"레시피"로 수집합니다. 레시피는 `source_recipes` 테이블에 저장되는 작은 JSON 구조체로, 목록 페이지
URL/페이지네이션 방식, 항목 선택자(CSS), 필드 매핑(제목/URL/기관/시작일/마감일이 어디 있는지),
필요하면 상세 페이지에서만 확인되는 필드까지 담습니다. 저장된 레시피가 있으면 매 수집은
`recipe_engine.run_recipe()`가 그 레시피만으로 결정적으로(추가 LLM 호출 없이, 무료로) 실행합니다.

사이트 구조가 바뀌어 수집이 갑자기 0건이 되거나 급감하면(이상감지), `collect_all()`이 자동으로
복구를 시도합니다 — 먼저 저장된 레시피를 그대로 재시도해보고(사이트가 일시적 문제였다면 이걸로
충분), 그래도 안 되면 LLM에게 페이지를 다시 보여주고 레시피를 새로 만들게 합니다(`discover_recipe_agentic()`,
필요하면 외부 JS 파일까지 열어보며 후보 URL을 검증). 관리자가 URL만으로 새 소스를 등록할 때도
동일한 발견 로직을 쓰며, 이 경우 미리보기를 확인하고 확정해야 실제 수집에 반영됩니다.

이 방식으로 바뀌기 전 손으로 짠 파서(K-Startup HTML 카드 구조 파싱, 서울바이오허브 `seq/gubun`
목록 조회 등)는 `collector.py`에 `collect_kstartup()`/`collect_nrf_iris()`/`collect_kddf()`/
`collect_biohub_direct()`로 참고용으로만 남아 있고, `collect_all()`은 더 이상 이 함수들을 호출하지
않습니다.

레시피 자체가 아예 안 맞게 됐을 때(예: 사이트가 완전히 리뉴얼됨) `config.json`에서 해당 소스의
`list_url`을 수정하면 다음 수집·복구 시도의 출발점이 바뀝니다. 그래도 안 되면 관리자 화면에서
소스 URL을 재정의하거나, 이상감지 자동 복구가 새 레시피를 발견하도록 기다리면 됩니다.

### 실행

저장소 폴더에서:

```powershell
python .\collector.py
```

서버가 켜져 있으면 관리자 화면의 **수동 재수집** 버튼(또는 웹 화면의 `업데이트` 버튼)으로도 동일하게 실행됩니다.

## KHIDI(보건산업진흥원) 직접 수집기

`boards.khidi_direct`도 게시판 크롤러가 아니라 KHIDI의 공개 openAPI 피드를 직접 호출하는 전용 파서입니다.

```text
https://www.khidi.or.kr/kps/openAPI/requestxml
```

이 피드는 공고 제목과 등록일만 내려주고 본문 텍스트는 주지 않으므로, `parse_title_dates()`가 제목
문자열 안에 섞여 있는 신청기간 표현(예: `(~7/31(목) 18:00까지)`, `2026.7.1~7.31`)을 정규식으로
해석해서 시작일/마감일을 추출합니다. 마감일만 뽑히고 시작일을 못 찾은 경우, 오늘 날짜부터
접수 중인 것으로 간주합니다.

```json
"khidi_direct": {
  "enabled": true,
  "menu_id": "MENU01108",
  "row_cnt": 200
}
```

KHIDI가 API 응답 구조나 `menuId`를 바꾸면 `config.json`의 `menu_id`를 조정하거나, `collector.py`의
`collect_khidi_direct()`/`parse_title_dates()`를 수정하면 됩니다.
